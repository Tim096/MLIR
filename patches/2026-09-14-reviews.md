## #223286 [APFloat] Fix sign bit corrupting exponent in unsigned FP8 formats（jay87406）

tgymnich 已 approve，CI Linux／Windows／AArch64 綠。第二個 commit 只是 merge main。你是被改的那個測試（#216056）的作者，所以這則的價值是「原作者確認」＋ follow-up 的方向。

**本機驗證**：
- bias 從 `APFloat.cpp` 讀：E8M0FNU `-127`（bias 127）、E5M3FNU `-14`（有 zero，bias 15）。
- 位元（python 算）：|2.0| 兩種格式都是 `0x80`，OR sign 看不出來；|1.0| E8M0 `0x7f → 0xff`（NaN 編碼）、E5M3FNU `0x78 → 0xf8`。PR 把 -2.0 換 -1.0 是對的。
- 根因：`convert()` L2668 回報 sign 遺失但不清 `sign`（測試也斷言 `isNegative()`），所以 `bitwiseIsEqual`（L1182 比 sign）與 `hash_value`（L3445 hash sign）仍把 -1.0／1.0 當不同值，儘管 bits 相同了。tgymnich 的 -Inf／-NaN assert 走的是 L2648 `makeNaN(false, sign)` → L942，同一個根因。

**要貼的 review（Comment）**：

> LGTM from the side of #216056, which added this test. I double-checked why the value has to change: with -2.0 the biased exponent is already 0x80 in both formats, so OR-ing the sign bit in is invisible; with -1.0 it turns E8M0FNU's 0x7f into 0xff (the NaN encoding) and E5M3FNU's 0x78 into 0xf8.
>
> For the follow-up from @tgymnich's list: the root cause is that `convert()` reports the lost sign but leaves `sign` set, so `bitwiseIsEqual` and `hash_value` still tell -1.0 and 1.0 apart in these formats even though their bits are now the same. I'll look at clearing the sign there, which may also take care of the two asserts, since the Inf/NaN paths pass that sign on to `makeNaN`.

## #220020 [APFloat] Signal overflow when rounding delivers the largest finite value（Garfield1002）

修 #220018：`IEEEFloat::handleOverflow` 在「rounding 給出最大有限值」那條路只回 `opInexact`，IEEE 754-2019 §7.4 要 overflow。patch：該路回 `opOverflow | opInexact`，`FiniteOnly` 格式除外；改 multiply／divide 的 quad 表與三張 FP8 add 表。兩週零 review，CI 除 code_formatter 外全綠，PR body 有揭露用 Claude Code。

**本機驗證**（連 `build/lib/libLLVMSupport.so`，**不含** patch，探針在 `scratchpad/apf/probe{,3}.cpp`）：

| 格式 | rounding | 操作 | 結果 |
|---|---|---|---|
| IEEEdouble | TowardZero | fromString 1e400／fromAPInt 2^1100／max+max／max×max | 最大有限值，`ovf=0` ← PR 要修的 |
| E5M2、E4M3FN | TowardZero／TowardNegative | max+max | 最大有限值，`ovf=0` |
| E2M1FN、E3M2FN（FiniteOnly） | **四種 rounding 全部** | max+max | 飽和到 6／28，`ovf=0`——連 nearest 都不報 overflow，所以 PR 排除 FiniteOnly 是和現況一致的 |
| PPCDoubleDouble | TowardZero | fromAPInt 2^1100 | 最大有限值，`ovf=0`——走 `DoubleAPFloat::handleOverflow`（L5555），PR 沒改到 |
| PPCDoubleDouble | TowardZero | fromString 1e400 | **assert crash**（L3489，legacy 轉 double 用 nearest 進位超過 DBL_MAX）——既有 bug，與 PR 無關 |
| PPCDoubleDouble | TowardZero | max+max、max×max | **`+Inf` 且 `ovf=0`**——往零捨入不該出 Inf，既有 bug，與 PR 無關 |

其他查證：
- `DoubleAPFloat::handleOverflow` L5579–5581：`S = opInexact; if (!getFirst().isFinite()) S |= opOverflow;`——有限值那條同樣不報。呼叫者只有 `convertFromUnsignedParts`（L5613／5676／5684）。
- L1733（significand 進位溢出）強制用往無限的方向，不受影響；L1745（NanOnly＋AllOnes）用原 rounding mode，PR 後會正確報。
- clang `SemaExpr.cpp` `BuildFloatingLiteral` L3832–3851：用 `FENV_ROUND` 的 rounding mode 解析字面值，`opOverflow` 就 `warn_float_overflow`。PR 後 `FE_TOWARDZERO` 下的 `1e400` 會開始警告（沒在本機 build clang，讀原始碼推得）。
- formatter：CI log 的 diff 確實重排整張 multiply `SpecialCaseTests`（舊式 `{ a, b }` 表）；但三張 FP8 表 `clang-format --lines` 只重排改到的 5 列（那 5 列超過 80 欄）。add／subtract／multiply／divide 四個測試都有 `const int OverflowStatus = APFloat::opOverflow | APFloat::opInexact;`。

**要貼的 review（Comment）**：

> Thanks for this, the IEEE 754 reading looks right to me. I checked the reproducer against current main, and with `IEEEdouble` too: under `rmTowardZero`, `convertFromString("1e400")`, `convertFromAPInt(2^1100)`, `max + max` and `max * max` all return the largest finite value with only `opInexact`.
>
> A few things I noticed while checking the other paths:
>
> 1. `DoubleAPFloat::handleOverflow` has the same finite-result branch: it only adds `opOverflow` when the high part is not finite. With `PPCDoubleDouble`, `convertFromAPInt(2^1100, rmTowardZero)` returns the largest value with only `opInexact`, so after this patch `IEEEdouble` and `PPCDoubleDouble` would disagree there. Could it get the same change, or a FIXME if you'd rather keep this PR to `IEEEFloat`?
>
> 2. Leaving out `FiniteOnly` formats matches what they already do under round-to-nearest: `Float4E2M1FN` and `Float6E3M2FN` saturate and return only `opInexact` in every rounding mode. It might be worth saying that in the comment, since otherwise it reads as if they were special-cased only here.
>
> 3. This is visible in clang: `BuildFloatingLiteral` parses literals with the `#pragma STDC FENV_ROUND` rounding mode and emits `warn_float_overflow` on `opOverflow`, so e.g. `double d = 1e400;` under `FE_TOWARDZERO` should start warning. That seems like the right behaviour, but since CI is green nothing covers it yet; a clang test would pin it down.
>
> 4. On the formatter: the `SpecialCaseTests` noise comes from that table predating clang-format, so leaving it seems fine to me. The FP8 rows you changed are over 80 columns though, and clang-format only rewraps those rows; a local `OverflowStatus` like the one in the add/multiply tests would also keep them short.
