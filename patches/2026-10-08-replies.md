## ⑦ APFloat 無號 FP8 follow-up（tgymnich 在 #223286 點名、本人 09-14 認領）

**分支** `apfloat-unsigned-sign`。三個問題：
- `-Inf`／`-NaN` 轉 `Float8E5M3FNU` 會 assert（`makeNaN(false, sign)` 帶著 sign）
- `E5M3FNU` 的 `1.0 - 1.5` 得到 `-0.5`，回 `opOK`
- （同一個根因）`-1.0` 轉成無號格式後 `isNegative()` 還是 true，bits 卻是 +1.0

**規則（convert 和 subtract 共用一條）：負的非零值沒有編碼 → NaN ＋ `opInvalidOp`；負零 → +0、負 NaN → NaN，只丟 sign（照舊回報 `losesInfo`／`opInexact`）。**

依據與取捨：
- **#216387**（chinmaydd，arsenm／krzysz00 review，09 月 merge）在 SelectionDAG 定義了 `convert.to.arbitrary.fp` 轉 E5M3FNU 的語意：「a negative input now saturates to zero when the saturate flag is set, and is poison otherwise. -0.0 is excluded from that and still converts to +0, and ... a negative NaN still produces the NaN encoding. APFloat treats constructing a negative value in an unsigned semantics as unreachable, so there was no existing behaviour to match.」APFloat 沒有 poison，對應的是 NaN ＋ `opInvalidOp`。本 patch 跟它逐條一致。
- 同一個檔案的 `convertToInteger`：負數轉 unsigned 回 `opInvalidOp`。
- 減法沒有硬體可以對照，用同一條規則。
- **另一條路（沒採用）**：NVIDIA CUDA Math API 對 ue5m3 是「the input sign is discarded first and then the absolute value is converted」，e8m0 也是對絕對值 round；MLIR `arith-expand` 的 E8M0 truncf 也是丟 sign。如果走這條，-1.0 會變成 +1.0，但減法 `1.0 - 1.5` 就得另外定規則（0.5 明顯錯）。**本人 09-14 在 #223286 寫的是「I'll look at clearing the sign there」，所以 PR 描述要說明為什麼最後改走 #216387 的語意。**
- MLIR 不受影響：`arith` 的 `convertFloatValue` 只要有任何 loss 或 status 不是 `opOK` 就不 fold。

**⚠️ 會推翻兩個既有的 death test**：#107127（E8M0）和 #210720（E5M3FNU）的作者都寫了 `EXPECT_DEATH(x.subtract(y) /* 4 - 8 */, "does not support signed values")`，也就是原本的設計是「結果是負數的減法屬於呼叫端的錯誤，直接 crash」。但 `1.0 - 1.5` 這種同 exponent 的情況根本不會走到那個 `llvm_unreachable`，所以原設計本來就沒擋住。本 patch 把 unreachable 拿掉、在 `addOrSubtract` 結尾統一處理（`0 - x` 走 specials 路徑也會被抓到），同時把兩個 death test 改成檢查 NaN。PR 描述要寫明這一點。

另外 #223286 加的 bits 比對（-1.0 和 1.0 轉換後 bits 相同）不再成立，因為 -1.0 現在變成 NaN；改成比對 NaN 的 bits。
